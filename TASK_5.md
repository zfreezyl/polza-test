## 3. Сравнение моделей

Сравниваю на одинаковом наборе задач, даю один и тот же промпт разным моделям и оцениваю:

- Работает ли код с первого запуска
- Читаемость и структура
- Обработка крайних случаев, пустой ввод, невалидные данные

Результаты записываю. При ежедневном использовании также замечаю паттерны, как: какие модели склонны к галлюцинациям, какие дают устаревшую информацию, какие лучше держат контекст в длинных диалогах



## 4. Тесты для новой функции

Для любой новой функции требую:

- **Happy path**: функция работает с корректными данными и выдаёт ожидаемый результат
- **Edge cases**: пустой ввод, максимальные или минимальные значения, границы допустимого
- **Error handling**: невалидные типы данных, отсутствующие поля, сетевые ошибки функция не падает, возвращает понятную ошибку
- **Интеграция**: корректно взаимодействует с другими частями системы (база данных, API,)





## 5. Разрешения для coding-агента

- **Терминал**: только внутри docker контейнера, без доступа к хостовой системе (Не `sudo`, нет прав на изменение системных файлов)
- **База данных**: только read-only на тестовой копии (Не `DROP`, `DELETE`, `ALTER`)
- **Файловая система**: любое изменение файлов требует подтверждения. Агент показывает diff, я подтверждаю
- **Сеть**: только к заранее указанным тестовым API.
- **Логирование**: все действия агента записываются, можно посмотреть, что именно он делал.




## 6. CI/CD и тесты

Автоматические тесты и CI/CD пока не использую на постоянной основе, но понимаю их важность и планирую внедрить при росте проектов

Перед слиянием и деплоем:

- **Линтинг**: проверка стиля и потенциальных ошибок
- **Проверка типов**: несоответствия типов ловятся до запуска
- **Unit-тесты**: все тесты пройдены, новый код покрыт тестами
- **Code review**: слияние только после проверки другим разработчиком
